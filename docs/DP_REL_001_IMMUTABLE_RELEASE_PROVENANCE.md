# DP-REL-001 — Immutable release provenance pipeline

**Status:** COMPLETE — repository implementation is merged and GitHub server-side release immutability was enabled by the repository owner on 2026-08-17.

**Canonical repository:** `arvectum/discount-parser`  
**Canonical integration branch:** `main`  
**Canonical future release tag convention:** `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-prerelease`

## 1. Goal

DP-REL-001 converts Discount Parser delivery builds into a durable provenance chain:

`canonical main commit -> immutable release tag -> one CI run -> exact build outputs -> SHA-256 manifest -> signed GitHub artifact attestations -> GitHub Release assets`.

The pipeline is deliberately fail-closed. It refuses to publish when the tag is malformed, the tagged commit is not reachable from canonical `main`, or a GitHub Release with the same tag already exists.

## 2. Canonical release convention

All new production/client releases use SemVer-style tags beginning with `v`:

- stable: `v1.0.0`, `v1.2.3`;
- prerelease: `v1.3.0-rc.1`, `v2.0.0-beta.2`.

Historical `r*` and `discount-parser-*` recovery tags remain provenance evidence and must not be renamed, moved, or deleted merely to match the new convention. The convention applies prospectively.

## 3. Pipeline behavior

The existing `.github/workflows/build-delivery.yml` continues to build the same Windows x64, macOS ARM64, and macOS Intel deliveries.

For a canonical `v*` tag push, a dedicated `release` job runs only after every platform build succeeds.

The release job:

1. checks out the exact tagged commit with full history;
2. validates the tag against the canonical version format;
3. fetches canonical `origin/main`;
4. proves the release commit is reachable from `origin/main` using `git merge-base --is-ancestor`;
5. proves the workflow SHA equals the tag target;
6. refuses to continue if a GitHub Release for that tag already exists;
7. downloads the exact three artifacts produced by the successful build matrix;
8. packages each delivery into a named ZIP;
9. generates `SHA256SUMS` for the release archives;
10. generates `release-provenance.json` with repository, tag, full commit SHA, workflow name, run ID, run attempt, workflow URL, artifact filenames, sizes, and SHA-256 values;
11. verifies the manifest against the bytes that will be released;
12. verifies `SHA256SUMS` before publication;
13. generates GitHub/Sigstore build provenance attestations with `actions/attest@v4`;
14. creates the GitHub Release as a draft with every asset already attached;
15. publishes the complete draft only after all assets are present;
16. re-reads the published Release API record and proves that the expected tag and assets are present.

This draft-first publication order follows GitHub's immutable-release guidance: complete the draft, attach all assets, then publish.

## 4. Durable release payload

Every future canonical release contains at minimum:

- `discount-parser-windows-x64.zip`;
- `discount-parser-macos-arm64.zip`;
- `discount-parser-macos-intel.zip`;
- `SHA256SUMS`;
- `release-provenance.json`.

The release provenance manifest is generated by `scripts/release_provenance.py` and independently regression-tested.

## 5. Cryptographic provenance

The release job grants only the permissions required for publication and attestation:

- `contents: write` — create the GitHub Release;
- `id-token: write` — obtain the short-lived OIDC identity used by GitHub artifact attestations;
- `attestations: write` — persist the signed attestations.

`actions/attest@v4` binds the released archive/checksum/manifest bytes to GitHub's workflow identity and source context. Consumers can verify the downloaded payload with GitHub CLI artifact-attestation verification in addition to SHA-256 checks.

Example verification after downloading an archive:

```bash
gh attestation verify discount-parser-windows-x64.zip --repo arvectum/discount-parser
sha256sum -c SHA256SUMS
```

## 6. Server-side immutable Releases setting

The repository pipeline never overwrites an existing Release and never moves a release tag. That is a repository policy control.

GitHub's **Enable release immutability** setting was enabled by the repository owner on 2026-08-17. The connected GitHub integration does not currently expose a reliable read endpoint for this setting, so this completion record is based on the owner's explicit confirmation after applying the setting in repository Settings.

With the setting enabled, future published Releases and their associated release tags are protected by GitHub's server-side immutable-release enforcement in addition to the fail-closed workflow policy.

## 7. Regression coverage

The release job also performs runtime verification before and after publication, so the static test suite is not the only gate.

## 10. Operational release procedure

1. ensure the intended release commit is on `main` and CI is green;
2. create a new immutable-name tag such as `v1.0.0` on that exact `main` commit;
3. push the tag to GitHub;
4. `build-delivery` builds all three platforms;
5. the release job validates ancestry, hashes and attestations;
6. a complete GitHub Release is created and published;
7. record acceptance against the exact release tag and SHA-256 from `SHA256SUMS`.

Never move or reuse a published release tag. If a release is bad, publish a new version tag.

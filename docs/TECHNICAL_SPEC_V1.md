# Discount Parser — техническое задание MVP v1.0

Статус: **зафиксировано для первой реализации**  
Дата: **2026-08-08**  
Репозиторий: `arutyunoveth/discount-parser`

## 1. Назначение

Система автоматически собирает скидки, промокоды, кэшбэк и предложения по доставке из заранее настроенного набора публичных источников, приводит их к единому формату, удаляет дубли, отслеживает актуальность и публикует подходящие предложения в Telegram-канал.

Основной пользователь первой версии — владелец Telegram-канала. Основной интерфейс управления — Telegram-бот. Таблица XLSX/CSV используется для просмотра, ручной корректировки и обмена данными, но **не является основной базой данных**.

Целевой конвейер:

```text
источники
  ↓
source adapters
  ↓
нормализация
  ↓
дедупликация
  ↓
классификация
  ↓
SQLite
  ↓
фильтры / очередь публикаций
  ↓
Telegram bot
  ↓
Telegram channel
```

## 2. Границы MVP

### 2.1. В MVP входит

1. Единое ядро парсинга с подключаемыми адаптерами источников.
2. Не менее **5 работающих источников** к моменту приёмки; целевой диапазон первой сборки — 5–10 источников.
3. Источники могут включать:
   - публичные сайты магазинов и агрегаторов скидок/промокодов;
   - публичные Telegram-каналы, если содержимое технически доступно без обхода авторизации/защит.
4. Регулярный автоматический сбор новых предложений.
5. Единая нормализованная база предложений.
6. Дедупликация внутри одного источника и между разными источниками.
7. Определение категории и подкатегории правилами.
8. Ручная корректировка категории/подкатегории через экспорт/импорт таблицы с сохранением пользовательского приоритета.
9. Запоминание безопасных классификационных правил из ручных корректировок.
10. Контроль срока действия и статуса предложения.
11. Ежедневная вечерняя проверка истёкших/устаревших предложений.
12. Фильтры публикации, включая минимальный процент скидки и категории.
13. Telegram-бот для просмотра состояния, очереди, настройки фильтра, предпросмотра и публикации.
14. Автоматическая публикация подходящих предложений в Telegram-канал.
15. Защита от повторной публикации одного предложения.
16. Экспорт актуальной базы в XLSX и CSV.
17. Технический журнал запусков и ошибок источников.
18. Автотесты ключевой бизнес-логики.

### 2.2. В MVP не входит

- универсальный парсер «всего интернета»;
- обязательная поддержка Ozon, Wildberries и Яндекс Маркета;
- обход CAPTCHA, антибот-защит, авторизации или иных ограничений сайтов;
- Playwright/Selenium как обязательная часть ядра;
- парсинг закрытых Telegram-чатов/каналов;
- LLM/нейросетевая классификация;
- генерация рекламных текстов через LLM;
- полноценная web-admin панель;
- многопользовательский SaaS;
- партнёрские ссылки и автоматическая подмена URL;
- аналитика кликов/конверсий;
- история цены товара как отдельный продуктовый модуль;
- автоматическое удаление исторических записей из БД.

Эти функции могут быть добавлены после обратной связи по первой версии.

## 3. Технологический стек

Базовый стек фиксируется следующим образом:

- Python `>=3.11`;
- FastAPI — служебный API и health endpoints;
- Pydantic Settings — конфигурация через `.env`;
- SQLAlchemy 2.x — ORM;
- SQLite — БД MVP;
- SQLite WAL mode — безопасная работа низконагруженных параллельных задач;
- Alembic — миграции схемы;
- `httpx` — HTTP-клиент источников;
- BeautifulSoup/lxml — HTML parsing;
- RapidFuzz — fuzzy matching для дедупликации;
- `aiogram` 3.x — Telegram bot/publishing;
- APScheduler — периодические задания MVP;
- openpyxl — XLSX export/import;
- PyYAML — конфигурация источников;
- pytest — тесты.

Для MVP предполагается один экземпляр приложения/worker. Горизонтальное масштабирование и распределённая очередь задач не требуются.

## 5. Источники и адаптеры

### 5.1. Конфигурация

Источники задаются в `config/sources.yaml`.

Минимальные поля:

```yaml
sources:
  - key: example_source
    name: Example Source
    type: website
    base_url: https://example.org
    adapter: example
    enabled: true
    priority: 100
```

Допускаются source-specific настройки: seed URL, категории, CSS selectors, rate limit, headers, pagination и т.д.

### 5.2. Контракт адаптера

Каждый адаптер должен:

1. получить сырые предложения;
2. вернуть список `RawOffer`/`OfferCandidate`;
3. не писать напрямую в Telegram;
4. не решать дедупликацию самостоятельно;
5. не изменять глобальные настройки;
6. изолировать ошибку конкретного источника от остальных источников.

Концептуальный интерфейс:

```python
class SourceAdapter:
    async def collect(self) -> list[RawOffer]: ...
    async def healthcheck(self) -> SourceHealth: ...
```

### 5.3. Выбор первых источников

Конкретный список внешних источников **не замораживается в ТЗ**, потому что доступность HTML/API и антибот-ограничения меняются.

Перед реализацией адаптера источник проходит короткий технический smoke-check:

- публичная доступность;
- стабильность структуры;
- наличие полезных полей;
- отсутствие обязательного CAPTCHA/login;
- приемлемая частота запросов.

Приёмочное условие MVP — минимум 5 реально работающих адаптеров, а не конкретные бренды любой ценой.

| `offer_type` | `promo_code`, `discount`, `cashback`, `delivery` |

| `description` | исходное/нормализованное описание |
| `discount_percent` | скидка, % |
| `discount_amount` | скидка, сумма |

| `old_price` | цена до скидки |
| `new_price` | цена после скидки |
| `cashback_percent` | кэшбэк, % |
| `cashback_amount` | кэшбэк, сумма |
| `delivery_amount` | стоимость/выгода доставки |
| `category` | категория |

| `valid_until` | окончание действия, если известно |
| `url` | исходная целевая ссылка |
| `canonical_url` | нормализованная ссылка |

Деньги хранятся как Decimal/Numeric, а не float.

## 7. Статусы и жизненный цикл

Минимальный набор статусов:

```text
new
needs_review
ready
published
expired
rejected
```

Правила:

- новое предложение создаётся как `new`;
- после достаточной нормализации оно становится `ready`;
- сомнительные записи получают `needs_review`;
- публикация переводит запись в `published`, но предложение остаётся в БД;
- истечение срока переводит его в `expired`;
- ручное исключение — `rejected`.

**Физически удалять истёкшие предложения из БД нельзя.** История нужна для предотвращения повторного добавления старой акции как новой.

## 8. Нормализация

Нормализатор выполняется отдельно от адаптеров и должен:

- очищать пробелы/HTML;
- нормализовать регистр и Unicode;
- приводить проценты и суммы к числовым полям;
- извлекать промокод, когда он явно указан;
- нормализовать URL;
- удалять tracking-параметры из URL по configurable allow/deny list;
- приводить даты к timezone-aware datetime;
- определять `offer_type`;
- сохранять исходные значения при невозможности уверенного преобразования.

Если критически важные данные неоднозначны, система не должна придумывать значение — статус `needs_review` предпочтительнее ложной точности.

## 9. Дедупликация

Дедупликация выполняется каскадом.

### Уровень 1 — точный внешний идентификатор

```text
source_id + source_offer_id
```

### Уровень 2 — канонический URL

```text
canonical_url
```

### Уровень 3 — промокод

```text
normalized merchant + normalized promo_code
```

### Уровень 4 — сигнатура предложения

Комбинация:

```text
merchant + normalized title + benefit + valid_until
```

с fuzzy matching через RapidFuzz.

Порог fuzzy match должен быть конфигурируемым и покрыт тестами.

При нахождении дубля:

- новая строка не создаётся без необходимости;
- обновляются `last_seen_at` и более качественные/свежие поля;
- сохраняется provenance источника;
- существующий `published` не возвращается в очередь публикации автоматически.

## 10. Категории и подкатегории

Первая версия использует детерминированную классификацию.

Приоритет:

1. ручной override;
2. сохранённое пользовательское правило;
3. mapping источника;
4. merchant/brand mapping;
5. keyword rules;
6. `Другое / Не определено` + `needs_review` при необходимости.

Базовые верхнеуровневые категории MVP:

- Продукты;
- Детские товары;
- Электроника;
- Бытовая техника;
- Одежда;
- Обувь;
- Красота и здоровье;
- Дом и быт;
- Доставка/сервисы;
- Другое.

Таксономия должна храниться в конфигурации/БД и расширяться без изменения кода.

## 11. Ручная корректировка и «обучение» правилам

Система экспортирует `offers.xlsx` с идентификатором записи и полями категории/подкатегории.

Пользователь может исправить значения и импортировать таблицу обратно через Telegram-бот или CLI.

При импорте:

1. текущая запись получает manual override;
2. parser не имеет права затереть manual override последующими запусками;
3. система может создать консервативное classification rule для аналогичных записей;
4. правило должно иметь понятный `match_key`, источник (`manual_import`) и возможность отключения;
5. неоднозначная коррекция применяется только к текущей записи, без широкого автоматического правила.

То есть «обучение» в MVP — это **rule memory**, а не ML.

## 12. Проверка актуальности

### 12.1. Явная дата окончания

Если `valid_until < now`, запись переводится в `expired`.

### 12.2. Предложение без даты окончания

Если источник позволяет повторно подтвердить наличие предложения, обновляется `last_seen_at`.

Запись без даты может быть признана устаревшей, если:

- она не встречалась заданное число последовательных обходов; или
- превышен configurable stale TTL.

Автоматическая политика должна быть консервативной, чтобы не удалять действующие бессрочные промокоды после одного сетевого сбоя.

### 12.3. Вечерняя задача

По умолчанию ежедневная maintenance-проверка запускается в `22:00` в timezone приложения. Время настраивается через `.env`.

Она:

- помечает истёкшие предложения;
- проверяет stale records;
- пересчитывает очередь;
- фиксирует статистику запуска.

## 13. Планировщик

Минимальные периодические jobs:

1. `collect_sources` — сбор новых предложений;
2. `expire_offers` — проверка сроков;
3. `build_publish_queue` — обновление очереди;
4. `autopublish` — публикация по активным правилам;
5. `maintenance` — вечерняя проверка/служебная статистика.

Периоды задаются конфигурацией. Повторный запуск одной job не должен создавать дубли.

## 14. Telegram-бот

### 14.1. Доступ

Бот административный. Разрешённые Telegram user ID задаются allowlist в `.env`.

Bot token и channel ID не хранятся в Git.

### 14.2. Основные функции

Минимальные команды/действия:

- `/start` — справка;
- `/status` — состояние системы;
- `/new` — новые предложения;
- `/queue` — очередь публикации;
- `/filter` — настройка фильтров;
- `/publish` — ручная публикация/подтверждение;
- `/autopost` — включение/выключение автопостинга;
- `/sources` — состояние источников;
- `/export` — получить XLSX/CSV;
- `/import` — загрузить исправленный XLSX.

Где возможно, используются inline-кнопки вместо необходимости помнить команды.

### 14.3. Фильтры

MVP должен поддерживать:

- минимальный `discount_percent`;
- категории;
- подкатегории;
- тип предложения;
- merchant/source при необходимости;
- наличие/отсутствие промокода;
- только актуальные и неопубликованные записи.

Основной пример заказчика — `discount_percent >= 20`.

### 14.4. Режимы публикации

1. **Preview/manual** — бот показывает предложение, пользователь подтверждает публикацию.
2. **Autopost** — система публикует записи, прошедшие сохранённый фильтр.

Автопостинг должен иметь ограничение количества публикаций за один цикл и минимальный интервал между постами.

## 15. Шаблон публикации

Текст строится детерминированно из данных Offer.

Пример скидки:

```text
🔥 Скидка 35% на детские подгузники Pampers

1 299 ₽ → 849 ₽

🏪 Детский мир
👶 Детские товары → Подгузники

⏳ До 12 августа

👉 Перейти к акции
```

Пример промокода:

```text
🎁 Скидка 20% по промокоду

Промокод: AGAIN20

🏪 Магазин X
⏳ До 15 августа

👉 Использовать промокод
```

Если есть корректное изображение, используется photo post с caption. При отсутствии изображения публикуется текстовый пост.

Шаблоны и emoji должны храниться отдельно от парсинга, чтобы оформление можно было менять без изменения source adapters.

## 16. Идемпотентность публикации

Должна существовать отдельная запись/ledger публикаций минимум с полями:

- offer_id;
- channel_id;
- telegram_message_id;
- status;
- published_at;
- error;
- template_version.

Уникальность `offer_id + channel_id` предотвращает случайную повторную публикацию.

Повторная отправка разрешается только явной пользовательской командой.

## 17. Экспорт и импорт

### Экспорт

Генерируются:

- `offers.xlsx`;
- `offers.csv`;
- при необходимости отдельный `run_report.json`.

В XLSX минимум листы:

- `active`;
- `needs_review`;
- `published`;
- `expired`;
- `sources_status`.

### Импорт

Импорт принимает только ожидаемые столбцы и ID существующих записей.

Разрешённые ручные изменения MVP:

- category;
- subcategory;
- title (как manual display title);
- status (`ready`, `rejected`, `needs_review`);
- при необходимости merchant/brand override.

Импорт не должен позволять случайно перезаписать системные идентификаторы и историю публикаций.

## 18. Наблюдаемость и аудит

Для каждого запуска парсинга сохраняются:

- start/end time;
- source;
- fetched count;
- new count;
- updated count;
- duplicate count;
- review count;
- errors;
- duration.

Ошибки одного source adapter не останавливают остальные источники.

FastAPI предоставляет минимум:

```text
GET /health
GET /health/db
GET /health/sources
```

## 19. Конфигурация

`.env.example` должен описывать минимум:

```text
DP_ENV=local
DP_DATABASE_URL=sqlite:///./data/discount_parser.db
DP_TIMEZONE=Europe/Moscow
DP_TELEGRAM_BOT_TOKEN=
DP_TELEGRAM_CHANNEL_ID=
DP_TELEGRAM_ADMIN_IDS=
DP_AUTPOST_ENABLED=false
DP_PARSE_INTERVAL_MINUTES=
DP_MAINTENANCE_HOUR=22
```

Точное имя переменной `AUTOPOST` должно использовать корректное написание в реализации; пример выше описывает требуемую настройку, а не совместимость с опечаткой.

Все секреты — только через env.

## 20. Надёжность HTTP-сбора

Общий HTTP-клиент должен иметь:

- timeout;
- retries с backoff для временных сетевых ошибок;
- ограничение частоты запросов;
- понятный User-Agent;
- обработку redirect;
- поддержку кодировок;
- отдельный source health status.

Система не реализует обход CAPTCHA/anti-bot. Если источник становится недоступен, он помечается degraded/blocked и не ломает остальной pipeline.

## 21. Тестирование

Обязательные unit/integration tests MVP:

1. URL normalization;
2. benefit/price parsing;
3. date parsing;
4. exact dedup;
5. fuzzy dedup;
6. duplicate update вместо duplicate insert;
7. manual override priority;
8. classification rule application;
9. expiration by date;
10. stale logic без ложного истечения после одного failure;
11. publish filter `discount >= N`;
12. publication idempotency;
13. export/import roundtrip для разрешённых полей;
14. source adapter fixture test минимум для каждого адаптера;
15. Telegram renderer/template test без реальной отправки.

Live network tests не входят в обязательный offline test suite.

## 22. Критерии приёмки MVP

MVP считается готовым, если одновременно выполняются условия:

1. Приложение запускается из чистого окружения по инструкции README.
2. БД создаётся/мигрируется без ручного редактирования.
3. Работает минимум 5 реальных source adapters.
4. Один полный parsing cycle завершается без падения всего приложения при ошибке одного источника.
5. Новые записи сохраняются в единой схеме.
6. Повторный парсинг не размножает те же предложения.
7. Cross-source дубли схлопываются с приемлемым качеством на тестовом наборе.
8. Истёкшие записи перестают попадать в выдачу/очередь, но остаются в истории.
9. Фильтр `скидка >= 20%` работает.
10. Telegram-бот показывает очередь и может вручную опубликовать выбранную запись.
11. Autopost публикует только подходящие активные неопубликованные записи.
12. Одна запись не публикуется повторно случайно.
13. Пост содержит название, выгоду, магазин/бренд при наличии, срок, ссылку и изображение при наличии.
14. XLSX экспорт открывается и содержит ожидаемые статусы.
15. Исправленные category/subcategory можно импортировать обратно без потери системных данных.
16. Manual override переживает повторный парсинг.
17. Вечерняя maintenance job обрабатывает expiry/stale state.
18. `pytest` проходит на обязательном offline наборе.
19. В README описаны запуск, env, подключение Telegram-бота и добавление нового source adapter.

## 24. Принципы реализации

1. Сначала корректность и идемпотентность, затем количество источников.
2. Source-specific code не должен проникать в core.
3. История важнее «чистой таблицы»: expired/duplicates не уничтожаются без необходимости.
4. Ручные пользовательские исправления имеют приоритет над автоматикой.
5. Любая автоматическая публикация должна быть воспроизводима из записи БД и версии шаблона.
6. Ошибка одного источника не должна останавливать весь сервис.
7. Любое расширение после MVP должно добавляться через adapters/rules/config, а не переписывать ядро.
